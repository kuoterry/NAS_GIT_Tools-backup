# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this folder.

## What this is

Single-file PyQt6 GUI tool (`key_management.py`) that scans the local machine for SSH keys (OpenSSH format + PuTTY `.ppk`), organizes them into a report, and provides management actions (generate, archive/delete, backup, restore). It is **independent** of the sibling `NAS_GIT_Tools` project one directory up — no imports, no shared code. Treat this as its own project. The one exception is the optional cross-machine sync feature (see "Cross-machine sync" below): a read-only peek at NasGitConnector's `QSettings` to prefill connection info, and pushing/pulling this tool's own registry metadata (never private key content) through a shared file on the NAS — narrow, opt-in, and the mirror image of the existing `key_management_registry_pubkeys()` bridge that runs the other way (NasGitConnector reading this tool's `registry.json`).

## Commands

```
pip install -r requirements.txt   # PyQt6
python .\key_management.py        # run the GUI
build_exe.bat                     # build dist\KeyManagement.exe (onefile/windowed, via PyInstaller)
```

`tests/test_key_management.py` holds `unittest`-based regression tests for the pure functions (pubkey/RFC4716/ppk parsers, `classify_private_key_file` — verified against real `ssh-keygen`-generated keys where available — `build_advisories`, `rewrite_ssh_config_identity`, `merge_registries`); run with `py -m unittest discover -s tests` from this folder. Deliberately stdlib-only. Every parser bug in this file's history was found by real key files, not synthetic ones — when the next one surfaces, fix it *and* pin the offending shape here. GUI/Worker behavior is still verified manually (`python -c "import key_management"` for a quick syntax/import check); no linter or CI config.

Current version is tracked in the `__version__` constant near the top of `key_management.py` and shown in the window title; bump it whenever a feature-level change lands. `build_exe.bat` produces two files in `dist\`: the stable `KeyManagement.exe` (desktop-shortcut target, name never changes) and a versioned copy `KeyManagement_v<__version__>.exe` (auto-copied, version read out of the `.py` source via `get_version.py`, not an inline `python -c` — see "Build tooling" in the sibling `NAS_GIT_Tools/CLAUDE.md` for why) — same convention as the sibling `NAS_GIT_Tools` project's `build_exe.bat`.

## Architecture

- **Pure functions first** (`parse_pubkey_line`, `parse_rfc4716_pubkey`, `parse_pubkey_file`, `ssh_fingerprint`, `describe_key_strength`, `classify_private_key_file`, `parse_ppk_pubkey`, `derive_pubkey_via_sshkeygen`, `scan_folder`, `build_advisories`, `build_records`, `parse_icacls_broad_principals`/`check_private_key_permissions` — loose-ACL detection, full-short-name matching so an account like `Git_User1` can't be false-positived by a `user` substring, silent-on-uncertainty because it feeds an advisory) — no Qt dependency, so they're testable by direct import. `build_records(folders, errors=None)` is the main entry point: normalizes/dedupes the folder list (dropping folders nested inside another selected folder — duplicate/nested folders used to produce phantom duplicate `.ppk` records and a false same-fingerprint advisory), walks folders (`scan_folder` returns a fourth value, `{path: classification}`, so private keys aren't read twice; `os.walk` reports unreadable subtrees into `errors` and prunes `.git`/`node_modules`-style noise dirs), classifies every file as public key / private key / PuTTY `.ppk` (a malformed `.ppk` returns `None` instead of raising through the whole scan), pairs pub+priv by matching basename in the same directory, computes fingerprint/strength/advisories, and returns a list of record dicts. `derive_pubkey_via_sshkeygen` returns `(publine_or_None, reason)` so the orphan-key advisory can say *why* derivation failed (no ssh-keygen / timeout / bad key).
- **`Worker(QThread)`** — same pattern as the sibling NAS tool (all filesystem/subprocess work happens off the UI thread), but this is an independent implementation, not shared code. Modes: `scan`, `generate`, `delete` (archive or hard, via `hard` param), `backup` (plain copy, or AES-encrypted zip when a `zip_passphrase` is passed — the zip path needs the optional `pyzipper` dependency; without it the UI offers plain copy only), `list_archive`, `restore_archive`, `purge_archive`, `read_private_raw`, `list_known_hosts`, `delete_known_hosts_entry`, `sync_registry`, `encrypt_key` (retrofit a passphrase onto an unencrypted non-ppk private key via `ssh-keygen -p` in place — same `input=""`/timeout/masked-`-N` conventions as `generate`), `rotate_key` (local rotation: generate new pair → optionally rewrite `~/.ssh/config` `IdentityFile` lines from old to new path via `rewrite_ssh_config_identity()` (backup-before-rewrite, `_norm_path` comparison so quoting/case don't cause misses) → optionally archive the old pair; deliberately does NOT touch any remote `authorized_keys` — NAS-side swap stays in NasGitConnector's 金鑰輪替, preserving the two tools' one-way-read-only boundary), `list_agent_keys` (`ssh-add -l`, rc 1 = empty agent is success-with-zero, rc 2 = no agent is an error; Pageant is explicitly out of scope), `convert_ppk` (shell out to `puttygen <ppk> -O private-openssh`; an encrypted ppk's passphrase goes through a temp file + `--old-passphrase`, never argv; CLI support varies by puttygen build so failures surface raw stderr plus a GUI-alternative hint), `rebuild_pub` (regenerate a stale `.pub` from its private key via the existing `derive_pubkey_via_sshkeygen`, backing the old `.pub` up first — the fix for a `pair_mismatch` finding), `compare_authorized_keys` (read-only `cat` of the *sync identity's own* `~/.ssh/authorized_keys` on the NAS via `_sync_ssh`, fingerprints matched against the current scan + registry into 兩邊都有/只在 NAS/只在本機 — the verification closing the rotation loop; revoking stays NasGitConnector's job, this never writes). Thread-lifecycle rules (2026-07-31 hardening): every `self.worker = Worker(...)` reassignment must be preceded by `keep_worker_alive(self)` (parks a still-running previous thread in `_retired_workers` until `finished` — rebinding in a done-handler otherwise drops the last reference to a not-quite-finished QThread and aborts the process); `MainWindow` guards close via `closeEvent`, but the three Worker-owning dialogs override `done()` instead, because `accept()`/Esc never pass through `closeEvent`. `MainWindow._busy` also disables the known_hosts/sync/registry buttons — the sync dialog and a running scan both write `registry.json`, so letting them overlap was a two-writer race. Unlike the sibling tool, this `Worker` also does its own local file I/O (`load_registry`/`save_registry`, not just network/subprocess) as its own established convention — `sync_registry` follows suit, doing the whole pull → merge → save-locally → push round-trip in one Worker call rather than splitting it across the UI thread the way NasGitConnector's `profile_sync_pull`/`profile_sync_push` do.
- **`MainWindow`** — folder list (default `~/.ssh`, user can add more, e.g. wherever `.ppk` files live) → scan → `QTableWidget` report → per-row actions (generate new pair, archive/hard-delete selected, backup, view raw private content, copy public key, open containing folder) → archive-region management dialog (`ArchiveManageDialog`) → audit log viewer (`AuditLogDialog`) → known_hosts manager (`KnownHostsDialog`) → sync config (`SyncConfigDialog`) → cross-machine overview (`SyncOverviewDialog`) → CSV export. **Fixed 2026-07-16 (code review):** `_busy(b)` used to only disable `scan_b`/`gen_b`/`archive_mgmt_b`/`audit_b`/`export_b` — the per-row destructive buttons (`archive_del_b`, `hard_del_b`, `backup_b`, `view_raw_b`) stayed clickable even while `on_archive_delete`/`on_hard_delete`/`on_backup` had already called `_busy(True)` and were mid-flight, and `on_view_raw` didn't call `_busy()` at all. That let a double-click (or clicking a second destructive action before the first Worker finished) spawn a second `QThread` against the same file — a real crash/race risk, not just a UI nit. `_busy()` now also disables those four buttons, and `on_view_raw` now follows the same `_busy(True)` / `_on_view_raw_done` → `_busy(False)` pattern every other destructive action already used. A follow-up diff review of this same fix caught that its scope stopped at `MainWindow` — `ArchiveManageDialog` (`refresh_b`/`restore_b`/`purge_b`) and `KnownHostsDialog` (`refresh_b`/`delete_b`) have their own `self.worker` and the exact same unguarded pattern, just never touched by the original fix. Both dialogs now have their own small `_busy()` disabling their own buttons, wired into every place they call `self.worker = Worker(...)`.

### SSH config awareness (`~/.ssh/config`)

`parse_ssh_config(path)` reads `Host`/`Match` blocks and their `IdentityFile` lines, building `{normalized_identity_path: [host_alias, ...]}`. It understands both plain `Host <alias>` blocks and `Match Host <h> User <u>` blocks (treating the `Host` value inside `Match` as the alias too) — it does **not** follow `Include` directives, since personal configs rarely use them and it'd add real complexity for little payoff. `build_records()` calls this once per scan and attaches `ssh_config_hosts` to every record with a `priv_path`, surfaced as the "SSH config Host" report column — this is what turns the report from "here's a key" into "here's a key, and here's what it's actually wired up to connect to." Path comparison goes through `_norm_path()` (expanduser + normcase + normpath) so Windows path-separator/case differences between the config file's `IdentityFile` value and the scanned file path don't cause false negatives.

`GenerateKeyDialog` has an optional "同時寫入 SSH config" group box (alias / HostName / User fields); if checked, `Worker._run_generate` calls `append_ssh_config_host()` after a successful `ssh-keygen` run. That function refuses to write if the alias already exists as a `Host` line anywhere in the file — it reports the conflict back rather than risking silently duplicating or shadowing an existing block. This exists because of a real incident: `nas_git_connector.py`'s `_ssh()` never passes `-i <identity file>` — it relies entirely on SSH's default key search plus whatever's in `~/.ssh/config`/the agent — so a freshly-generated key with a non-default filename (e.g. `id_ed25519_git_user2`) is invisible to that tool's connection test until an SSH config entry (or `Match ... User ...` block, for the common case of one host with multiple per-account identities) points at it explicitly.

**Fixed 2026-07-16 (code review):** `append_ssh_config_host()` wrote the `IdentityFile` value unquoted (`IdentityFile {identity_path}`), even though `parse_ssh_config()` already does `.strip('"')` on read — implying quoted values were always an expected format this file anticipated, just not on the write side. A path containing a space (a common Windows path shape — user profile names, `OneDrive - Company Name`, etc.) would make OpenSSH's own config parser stop at the first space and look for the wrong, truncated path — silently reproducing the exact "key invisible to `ssh`" failure this whole feature exists to prevent. Now writes `IdentityFile "{identity_path}"` (quoted), matching the read side.

**Fixed 2026-07-16 (real incident, not just a review finding):** `append_ssh_config_host()` only ever wrote a plain `Host <alias>` block — which only takes effect if the admin actually types `ssh <alias>`. Every real caller (`nas_git_connector.py`'s `_ssh()`, or a plain `ssh user@host` at a terminal) connects with the literal `user@hostname`, never an alias, so the "同時寫入 SSH config" checkbox's whole point — solving "one host, multiple per-account identities" — never actually worked for the tool it was built to unblock. This surfaced for real: a freshly-generated `git_user2` key was added to the NAS correctly, but connecting still fell back to `Permission denied (publickey,password)` on the machine that held the new (non-default-named) private key, because nothing pointed `ssh` at it — the admin had to hand-write a `Match originalhost <host> user <user>` block themselves before it would work. `append_ssh_config_host()` now writes exactly that (`Match originalhost {hostname} user {user}` + `IdentityFile`) whenever `user` is provided — it takes effect automatically for any `ssh user@hostname` or `git push`/`_ssh()` call, no alias typing required, and correctly handles "same NAS host, several accounts" without one identity's config clobbering another's. The old plain `Host <alias>` form is kept as a fallback only when `user` is left blank (single-identity, alias-typing convenience case). `parse_ssh_config()`'s `Match` regex was widened (`\b(?:originalhost|host)\s+(\S+)`) so the report's "SSH config Host" column still recognizes these new-style blocks, not just the old `Match Host ...` form. `GenerateKeyDialog`'s "Host 別名" field is now optional whenever "User" is filled in.

### known_hosts management

`parse_known_hosts()` / `delete_known_hosts_entry()` (backed by `list_known_hosts` / `delete_known_hosts_entry` Worker modes, surfaced via `KnownHostsDialog`). Duplicate detection groups by **`(host, key_type)`**, not just `host` — a single host legitimately has separate entries for ed25519/ecdsa/rsa etc. when the client has accepted multiple algorithms over time, and that's normal, not a problem; only the same host *and* the same key type appearing more than once is a real "stale entry from before a key rotation" signal. (First implementation grouped by `host` alone and flagged the completely normal multi-algorithm case as "duplicate" — caught by testing against the user's real 7-entry `known_hosts`, not synthetic data; a lesson worth repeating for any future parsing code in this file.) Hashed hostnames (`|1|salt|hash`, OpenSSH's `HashKnownHosts` default) can't be de-duplicated at all this way since each gets a fresh salt even for the same host — those are listed as "（已雜湊，看不出主機名）" and never flagged. Deletion backs up the whole file first (`.bak-<timestamp>`), same convention as everywhere else destructive in this codebase.

### Public key format support

Two on-disk public key formats are recognized, both routed through `parse_pubkey_file(path)`:
- Single-line OpenSSH (`ssh-rsa AAAA... comment`) — `parse_pubkey_line`.
- Multi-line RFC 4716 / SSH2 (`---- BEGIN SSH2 PUBLIC KEY ----` ... `Comment: "..."` ... base64 body ... `---- END`) — `parse_rfc4716_pubkey`. This is what some PuTTYgen versions produce for "export OpenSSH key" instead of the single-line form; found and fixed by testing against the user's real `~/.ssh` (`putty_id_rsa.pub` was silently unparsed before this was added — always test new key-file-format code against real key files, not just synthetic ones).

`.ppk` files are handled separately (`parse_ppk_pubkey` extracts the `Public-Lines:` block directly — always plaintext even when the private part is encrypted) since they bundle pub+priv in one file rather than needing basename pairing.

### Security boundaries (these are load-bearing, not just comments)

- **Private key content is never read except in exactly one place**: `Worker._run_read_private_raw`, which only runs when the user explicitly clicks "檢視私鑰原始內容…" and confirms a warning dialog — and that action is itself written to the audit log. Every other code path that touches a private key file (`classify_private_key_file`, `_is_openssh_v1_encrypted`) only reads header bytes / wire-format metadata (format, encrypted true/false) — never the key material itself.
  **Fixed 2026-07-16 (code review):** `_is_openssh_v1_encrypted`'s docstring always claimed this, but the code actually `base64.b64decode`'d the *entire* key body before reading the cipher-name field a few bytes in — for an unencrypted key, the full plaintext private key material briefly existed in a local `blob` variable, contradicting the function's own stated contract. Nothing ever logged/returned/cached that variable, so this was never actually exploitable, but it was a latent trap for any future edit that did. Now decodes only the first 128 base64 characters (~96 bytes — comfortably covers the 15-byte magic plus the cipher-name's length-prefixed string), never touching the rest of the body.
- **`derive_pubkey_via_sshkeygen`** only runs against private keys already confirmed unencrypted (`priv_encrypted is False`) — it shells out to local `ssh-keygen -y -f <path>` with `input=""` and a 5s timeout so it can't hang waiting on a passphrase prompt it was never meant to trigger.
  **Fixed 2026-07-16 (code review):** `Worker._run_generate`'s own `ssh-keygen -t ... -f <path>` call (the one that actually *creates* a new key pair) had neither of those guards — no `input=""`, no `timeout=`. The exists-check just above it is a TOCTOU check, not atomic with the keygen call, so if `ssh-keygen` ever fell back to an interactive prompt, the Worker thread would hang forever with the busy state never clearing. Now passes `input=""` and `timeout=30` (generous enough for a slow RSA-4096 generation), matching `derive_pubkey_via_sshkeygen`'s existing convention.
  **Also fixed 2026-07-16 (code review):** that same call's `self.log.emit(...)` line printed the full `ssh-keygen` argv, including the freshly-chosen `-N <passphrase>` value, in plaintext — the one place in this file that logged key material outside the deliberate `_run_read_private_raw` boundary above. (Inert in practice, since nothing currently connects to `Worker.log` for the generate flow — but a real landmine for whoever wires up a log pane next.) The logged command line now masks the `-N` argument as `***`; the actual `subprocess.run` call still gets the real passphrase.
- **CSV export defaults to excluding private key content.** `on_export_csv` always asks (Yes/No, default No) before including raw private key text as an extra column — because a CSV, unlike the GUI, is a file that gets emailed/copied/uploaded, so this is the one export path where accidental broad exposure is a real risk distinct from the user's own read access to their own files.
- None of the above is about restricting the user (this tool assumes the user is the sole admin of their own machine) — it's about not being the thing that turns "a private key sitting in a folder" into "a private key sitting in an easily-shared report."

### Local state: `~/.key_management/`

- `registry.json` — persistent key inventory, keyed by fingerprint (falls back to file path for keys that can't be fingerprinted, e.g. encrypted orphan private keys with no matching public key). Written atomically (temp + `os.replace`); a corrupt file is renamed `.corrupt-<ts>` and audited instead of silently becoming `{}` (which the next save would have turned into permanent history loss). `history` records state *transitions* only (not one `scanned` per scan) and is capped at `HISTORY_CAP` (200) per entry — uncapped history once meant the sync payload would eventually exceed Windows' 32767-char argv limit, which is also why the sync push now feeds base64 via stdin. The scan's missing-flip skips entries whose `seen_hosts` doesn't include this machine (entries merged in from other machines are unscannable here by definition). `RegistryDialog` (「名冊歷史…」) is the read/prune UI over this file — the only thing that ever shrinks it. Updated on every scan via `update_registry_from_scan()`: upserts `last_seen`/metadata for everything found, and flips previously-`active` entries not seen in the current scan to `status: "missing"` (not `"deleted"` — the tool doesn't assume *why* something vanished, it just wasn't found in this scan's folder set). Each entry accumulates a `history` list of `{ts, action}` events. This is what makes the tool's "紀錄" (record-keeping) promise real — the report table is a live snapshot, the registry is the durable history.
- `audit.log` — plain append-only line per management action (`generate`, `archive`, `delete_hard`, `backup`, `restore`, `purge_archive`, `view_private_raw`, `export_csv`, `encrypt_key`, `rotate_key`, `convert_ppk`, `rebuild_pub`), same tab-separated timestamp/action/detail convention as the sibling NAS tool's `audit_log()`, but this is a separate function/file, not shared.
- `archive/<timestamp>/` — where "封存（安全刪除）" moves files (default, reversible delete path); "永久刪除…" requires typing the exact filename to confirm and skips the archive entirely (same two-tier delete philosophy as the sibling tool's repo deletion, reused here for keys).
- `sync_config.json` — cross-machine sync connection settings (`host`/`user`/`remote_root`/`identity_file`), written by `SyncConfigDialog`. Key-based auth only; there is no password field and no `plink` fallback anywhere in this file, unlike the sibling tool.

### Cross-machine sync (opt-in; the only place this tool ever touches the network)

For a single admin using multiple machines, `SyncOverviewDialog` ("🌐 跨電腦金鑰總覽…") and the `sync_registry` Worker mode push/pull this tool's own key-registry **metadata** — never private key content — through a shared file on the NAS, `<remote_root>/config/km_registry_sync.json`, written the same base64 + `mkdir -p` + timestamped-backup convention `nas_git_connector.py` already uses for `tg_bot.conf`/`profiles_sync.json`. `_sync_ssh()` is a small, independent SSH-call helper (key-based only, no `plink`) — deliberately not shared code with the sibling tool's `_ssh()`, just matching its conventions (`BatchMode=yes`, `StrictHostKeyChecking=accept-new`, `-i <identity_file> -o IdentitiesOnly=yes`).

`merge_registries(local, remote, hostname)` does the actual merge: key selection matches `update_registry_from_scan`'s existing convention (fingerprint, or path as a fallback); the entry with the newer `last_seen` wins for metadata fields, **except `MACHINE_LOCAL_FIELDS`** (`pub_path`/`priv_path`/`priv_format`/`priv_encrypted`/`status`), which always keep the local value — they describe *this machine's* disk, and letting another machine's newer `last_seen` overwrite them broke both the local report and the `key_management_registry_pubkeys()` bridge (it would offer a `pub_path` that only exists on the other machine); before overwriting the local registry with the merged result, a `.bak-<ts>` copy is kept (backup failure aborts the sync); `history` lists are concatenated and de-duplicated by `(ts, action)`; and a new `seen_hosts: {hostname: last_seen}` field is **unioned, never shrunk** — this is what lets a fingerprint's presence on multiple machines be detected at all, since a single machine's own scan has no way to know what other machines hold.

This is what extends the two advisories that already existed *before* this feature — the RSA-bit-count / DSA-deprecation / age (`mtime > 730 days`) checks and the same-scan duplicate-fingerprint check in `build_advisories()` — from single-machine to cross-machine scope, **without changing their existing logic**: `build_records()` now also loads the local `registry.json` once per scan (already-synced data, no network call needed for this) and passes a `{fingerprint: {hostname: last_seen}}` map into `build_advisories()`; if a fingerprint's `seen_hosts` includes any hostname other than the current machine's, a new advisory line is appended. A key that's never been synced simply has no `seen_hosts` data and behaves exactly as before this feature existed.

`read_nas_git_connector_profiles()` (now also returning each profile's `machines` hostname-binding list) is the read-only peek at `QSettings("TerryTools","NasGitConnector")` behind `SyncConfigDialog`'s "從 NasGitConnector 帶入…" button — and behind `nas_git_machine_labels()`/`label_host()`, which translate hostnames into the sibling tool's profile labels (家中/公司) in the window title, the cross-machine advisory, `SyncOverviewDialog`, and `compare_authorized_keys` (whose report now resolves remote-only keys against registry `seen_hosts`: a key another synced machine holds shows as 🖥「<機器（標籤）>上的金鑰（正常）」instead of a ❓; registry entries seen only on *other* machines no longer count as 本機有). All of it degrades to plain hostnames when NasGitConnector isn't installed or nothing is bound — same file-format assumptions as that tool's own `_read_profile()` (`profiles/<name>/user`, `/host`, `/remote_root`, `/identity_file`). If the picked profile has no `identity_file` (a password-only identity), the import still fills `host`/`user`/`remote_root` but leaves `identity_file` blank with an explanatory status message, since this tool's sync has no password path at all.

## Scope notes

This was built as a genuine management tool (not read-only reporting) at the user's explicit request — "我公私鑰都要有管理與紀錄功能，把我當作超級管理者" (both public and private key management with record-keeping, treat me as the super-admin). It does not currently do: pushing new keys to remote `authorized_keys` files anywhere (local `rotate_key` exists — see the Worker mode list — but the remote half of a rotation is deliberately NasGitConnector's job), or scanning any location other than folders the user explicitly adds (no automatic whole-disk search). `build_records` now also *verifies* each unencrypted pub+priv pair (`ssh-keygen -y` re-derive, blob compare → `pair_mismatch` + a「重建 .pub」one-click fix): same-basename pairing was previously trusted blindly, and a stale/swapped `.pub` poisons the fingerprint — the primary key for the registry, cross-machine `seen_hosts`, agent inventory, and the NasGitConnector bridge — with zero warning. Encrypted private keys can't be verified (needs the passphrase) and stay silent. Every private key (ppk included) also gets a permissions check (`perm_loose` advisory): Windows OpenSSH silently ignores keys with loose ACLs and falls back to password auth — the same failure shape as the NAS home-dir ACL incidents. The 未加密-private-key advisory distinguishes ppk from non-ppk (only the latter gets the「加上密碼保護…」one-click fix; ppk points at PuTTYgen/conversion instead), and the key-age advisory threshold (default `DEFAULT_KEY_AGE_DAYS` = 730) is adjustable via the scan row's QSpinBox, persisted as `advisory_age_days` in QSettings and passed into `build_advisories()` as a parameter so the function stays pure/testable.

Two narrow, one-directional couplings with the sibling `NAS_GIT_Tools` project exist, both read-only, neither a hard dependency:
- The sibling project has a "從 Key_Management 匯入…" button in several of its dialogs that peeks at this tool's `registry.json` to let the admin pick a pubkey instead of copy-pasting it. That coupling lives entirely on the `NAS_GIT_Tools` side (`key_management_registry_pubkeys()` in `nas_git_connector.py`) — nothing in this file imports or knows about `NAS_GIT_Tools`. If `registry.json`'s schema changes (keys read: `status`, `pub_path`, `comment`, `type`, `fingerprint`), that reader needs updating too.
- This tool's own `read_nas_git_connector_profiles()` (see "Cross-machine sync" above) runs the other way: it peeks at the sibling project's `QSettings` to prefill sync connection info. If that tool's profile QSettings key layout changes (`profiles/<name>/user`, `/host`, `/remote_root`, `/identity_file`), this reader needs updating too.
