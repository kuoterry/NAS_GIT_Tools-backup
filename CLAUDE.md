# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

Single-file PyQt6 GUI tool (`nas_git_connector.py`, several thousand lines) that connects a local project folder to a Synology NAS Git server (`kcc3713.synology.me`, bare repos under `/volume1/Git_Server`). It also manages that Git server: browsing repos, per-repo CI policy, archive/restore, health checks, log viewing, GitHub mirror registration/sync. Written for a single user's home/office dual-machine workflow. Current version is tracked in the `__version__` constant near the top of `nas_git_connector.py` and shown in the window title; bump it (and the matching line in `NasGitConnector_說明書.docx`'s cover page) whenever a feature-level change lands, and rebuild via `build_exe.bat`'s PyInstaller command. That script produces two files in `dist\`: the stable `NasGitConnector.exe` (what the desktop shortcut should point at — name never changes across versions) and a versioned copy `NasGitConnector_v<__version__>.exe` (auto-copied, version read straight out of the `.py` source via `get_version.py` so it can't drift from the constant — see "Build tooling" below for why that's a separate script rather than an inline command) for keeping old builds around / side-by-side comparison. `Key_Management/build_exe.bat` follows the identical two-file convention for `KeyManagement.exe`. The two tools are versioned **independently** — Key_Management has its own `__version__` in `key_management.py` and its own `KeyManagement_說明書.docx` cover page, on its own numbering; don't bump one because the other changed, and don't expect the two numbers to line up. (Neither current version number is repeated here on purpose: read them from the two `__version__` constants, which can't go stale the way a copy in this file does.)

This repo also contains `Key_Management/`, a completely separate PyQt6 tool (own `CLAUDE.md`, own `requirements.txt`) for scanning/managing local SSH keys — unrelated to the NAS connector, no shared code or imports either direction. There are two deliberate, narrow, read-only exceptions to that independence, one each way: `key_management_registry_pubkeys()`/`pick_key_management_pubkey()` in `nas_git_connector.py` peeks at Key_Management's `~/.key_management/registry.json` so a pubkey can be picked from a dropdown instead of copy-pasted (see "Key_Management import bridge" below); and Key_Management's cross-machine sync feature peeks at this tool's `QSettings("TerryTools","NasGitConnector")` profiles to prefill NAS connection info instead of asking the admin to type it twice (see "Cross-machine profile sync" below, and Key_Management's own `CLAUDE.md`).

`HOWTO_新增SSH金鑰到NAS.md` is an end-user walkthrough (in Traditional Chinese) of the four key-provisioning scenarios covered by `CreateGitDevsUserDialog`/`AddKeyForUserDialog`/`RotateKeyDialog`/`SshKeysDialog` — read it for the user-facing "what button do I click" narrative; this file covers the "why does the code work this way" side instead, and the two deliberately don't repeat each other's content. `HOWTO_跨機器同步.md` is the same kind of end-user walkthrough for the cross-machine profile/registry sync feature (covers both this tool and `Key_Management`) — explains the merge rules (newest `updated_at`/`last_seen` wins per field, `machines`/`seen_hosts` always union) in plain language, since that's the part a button-by-button tour doesn't make obvious.

[`docs/INCIDENTS.md`](docs/INCIDENTS.md) holds the full post-mortem narratives for this repo. This file keeps only the durable outcome of each one — the rule, the invariant, or the code that exists because of it — and links there; go read the narrative when something fails in a way that resembles a past failure, since several of these entries record which *wrong* theories were ruled out, and that's usually the part that saves time.

A few loose top-level files are one-off or personal-workflow scripts, not part of the GUI tool itself: `fix_git_user3_home_acl.sh` is a point-in-time diagnostic/fix script written for the `git_user3` incident (see "Creating new `git_devs` accounts" below) and kept only as a historical reference, not a reusable tool — its ACL theory was later superseded by the home-directory-ownership root cause found for that same incident. `sync-git-identity.ps1`/`sync-git-identity.md` is an unrelated personal utility for keeping `git config user.name` distinct per machine across this user's own repos (home vs office), documented in its own `.md` — it has nothing to do with the NAS connector or the `git_devs` account system.

### This repo is subject to its own tool's CI rules

`origin` is `kuoterry@kcc3713.synology.me:/volume1/Git_Server/NAS_GIT_Tools.git` — this repo is hosted on the same NAS Git server this tool manages, so the "Server-side CI system" rules below apply to its own pushes: default/working branch is `develop` (no `main`/`master`), feature work on `feature/*`, commit messages prefixed `feat:`/`fix:`/`chore:`/`docs:`. Enforced remotely by `pre-receive.ci` at push time, so nothing local warns first.

### Branch naming and lifecycle

The CI hook only checks the `develop|feature/*|release/*` shape; everything below is the convention this repo has actually followed on top of that, recoverable from `git log --merges` and `git branch -a` but not from the hook.

- **Branch names are English kebab-case topics** (`feature/collapsible-identity-panel`, `feature/unify-telegram-email-notifications`, `feature/ci-engine-new-branch-fix`) even though commit messages and docs are Traditional Chinese — keeps `git branch -a` output aligned and typeable. No ticket ids (this repo has no tracker; the `[JIRA-n]`/`[TASK-n]` form the CI hook accepts is for other repos on that server), no dates, no author prefixes.
- **`release/*` is allowed by the hook but has never been used here.** Versions ship straight off `develop` plus a tag; there's no stabilization branch. Don't create one out of gitflow habit.
- **Not every change gets a branch.** Single-purpose docs/fix commits land directly on `develop` (that's most of the recent non-merge history). Branch when the work is multi-commit, or touches `nas_git_connector.py` behavior in a way that might need to be abandoned or reviewed as a unit.
- **Merge back with `--no-ff`**, merge-commit message `chore: 合併 <中文摘要> (feature/<name>)`. The no-ff merge commit is what makes a feature's commit set identifiable afterwards; a fast-forward would dissolve it into the linear history.
- **Merged branches are not deleted** — not locally, not on `origin` (decision 2026-07-27). They're the cheapest index of which commits made up a feature, and with one admin there's no branch-list clutter to pay for it. The consequence to remember: **branch count is not a work-in-progress signal.** `git branch -a --no-merged develop` (empty = nothing outstanding) is the only check that means anything here; a long `git branch -a` listing is expected and says nothing about unfinished work.
- **Tags use two independent namespaces**, matching the two independently-versioned tools: `v<x.y.z>` for the NAS connector, `key-management-v<x.y.z>` for Key_Management. Annotated, created after the version bump commit is pushed.

### Build tooling: version-tagged exe copy relies on `get_version.py`, not an inline `python -c`

`build_exe.bat`'s "[3/4] Tagging a versioned copy" step reads `__version__` out of `nas_git_connector.py` via `for /f "delims=" %%v in ('%PY% "%~dp0get_version.py"') do set "VERSION=%%v"`. `Key_Management/build_exe.bat` does the identical thing against `key_management.py` via its own `Key_Management/get_version.py`. Both `get_version.py` files are tiny (open the `.py` source, regex out `__version__ *= *"([^"]+)"`, `print()` the match) and exist for exactly one reason: don't put that regex inline as a `python -c "..."` string inside a batch `for /f ('...')` capture.

**The `.spec` files on disk are not the build input.** `NasGitConnector.spec` and `Key_Management/KeyManagement.spec` exist in the working tree but are PyInstaller-generated leftovers: `*.spec` is in `.gitignore`, neither file is tracked, and both `build_exe.bat` scripts invoke PyInstaller with explicit CLI flags against the `.py` source (`--noconfirm --clean --onefile --windowed --name <Name> … <script>.py`; the NAS-connector build also passes `--add-data` for the four `TOOL_SCRIPT_NAMES` server-side scripts so the frozen exe can deploy and hash-compare them), which *regenerates* the spec rather than reading it. Editing a `.spec` to change build behavior (adding `datas`, an icon, `hiddenimports`, …) silently has no effect — change the flags in the `.bat` instead, or switch the build command to take the `.spec` as its argument and track it first.

**Rule for any batch script in this repo:** never build a `for /f ('...')` capture around a `python -c "..."` string whose Python code itself needs to contain a literal `"`. `cmd.exe` has no `\"` escape — each one is just another quote toggling the parity `for /f` uses to find the end of the parenthesized command — so the line fails to parse, `VERSION` never gets set, and the build falls into its `[WARN]` branch while the main PyInstaller step still succeeds (i.e. it fails silently, which is how this survived unnoticed). Write a small `.py` file and call it instead — same "avoid quoting hell by moving content to a file" approach `nas_git_connector.py` already uses for base64-transported payloads (see `PATCHED_ENGINE_B64` in Architecture below). Full post-mortem, including why the CRLF theory was a red herring: [`docs/INCIDENTS.md`](docs/INCIDENTS.md) (2026-07-22).

## Architecture

Everything lives in `nas_git_connector.py`:

- **`Worker(QThread)`** — the only thing allowed to touch the network/filesystem/subprocess. Runs one "mode" per instantiation (`connect`, `test`, `list`, `delete`, `rename_repo`, `hooks`, `ci_status`, `set_ci`, `set_ci_batch`, `repo_detail`, `repo_desc_get`, `repo_desc_set`, `repo_files`, `file_content`, `repo_gc`, `repo_log`, `repo_branches`, `merged_branches`, `grep_all`, `repo_diff`, `tag_list`, `tag_create`, `tag_delete`, `file_blame`, `branch_protect_get`, `branch_protect_set`, `ssh_keys_list`, `ssh_keys_add`, `ssh_keys_delete`, `prep_new_user`, `local_gen_ssh_key`, `list_git_devs_users`, `clone`, `create_mirror`, `sync_mirrors`, `get_backup_remote`, `set_backup_remote`, `backup_sync`, `repo_fsck`, `upgrade_engine`, `healthcheck`, `disk_usage`, `repair`, `log`, `create_repo`, `ci_selftest`, `archive_list`, `archive_restore`, `archive_purge`, `tg_conf_get`, `tg_conf_set`, `profile_sync_pull`, `profile_sync_push`, `set_repo_kind`, `github_scan`, `local_scan`, `deploy_tools`), each dispatched in `Worker._dispatch()` (called by `Worker.run()`) to a `_run_<mode>` method — keep this list in sync when adding one. The authority on what is a mode is the `if/elif` chain in `Worker._dispatch()` (note `connect` is its trailing `else` fallback, not an explicit `elif`), **not** `grep "def _run_"` over the whole file: the `_run_*` prefix has historically also been used by dialogs for their own non-Worker methods (e.g. the since-removed `ArchiveDialog._run_next_purge`), so a file-wide grep can over-count and invent a mode that can't be dispatched. Grep within `Worker` only, or read the dispatch chain. Communicates back to the UI only via Qt signals (`log`, `done`, `repos`, `hooks`) — never touches widgets directly, to avoid cross-thread crashes. `Worker.run()` wraps the dispatch chain in try/except and converts any `_run_*` exception into `done(False, …)` — a silently-dead QThread would leave `set_busy(True)` stuck forever, which is exactly what used to happen. `_run()` is `Popen`-based: subprocess output is streamed line-by-line to the `log` signal in real time (long remote loops like healthcheck/sync show progress as it happens), supports a `timeout` (default 600 s per `_ssh` call, 3600 s passed explicitly by gc/fsck/sync/clone/repair/healthcheck; rc=124 on expiry) and cooperative cancellation via `Worker.cancel()` (rc=125) — wired to the global「⛔ 中止」corner button on the tab bar, and `MainWindow.closeEvent` cancels+waits instead of hard-killing a running thread. All NAS interaction goes through `_ssh()` (keyless `ssh` by default — with `ServerAliveInterval` so a dead peer is detected in ~60 s — or `plink` if a password is set; the password goes through a temp file + `-pwfile` (PuTTY ≥ 0.77) so it never appears on the process command line, with automatic one-shot fallback to `-pw` for older plink) and remote commands are shell scripts built as `"\n".join([...])` heredoc-style, delimited by `___BEGIN___`/`___END___` markers that `_between()` strips out to filter SSH login banners. Values that aren't whitelist-checked by `is_safe_name` (branch names, file paths, search patterns, SSH key lines) go through `shq()` for POSIX single-quote escaping before being interpolated into a remote command. Multi-line/binary-ish payloads (repo description text, README/.gitignore template content) are instead base64-encoded client-side and piped through `base64 -d` on the remote end, the same convention `PATCHED_ENGINE_B64` already used — avoids quoting hell entirely rather than trying to shell-escape arbitrary text. New remote scripts should go through `_ssh_block(lines, timeout=…) -> (ok, body, err_hint)` instead of hand-rolling the marker wrapper; it centralizes `_between()`, timeout, and squeezing stderr into a one-line reason (`_err_hint`) that failure messages now append instead of the old guess-only「連線或權限問題」. `local_gen_ssh_key` is the one mode that never touches the NAS at all — it runs `ssh-keygen` on the admin's own machine via `self._run()` (the same local-subprocess helper used for `git clone`).
- **`MainWindow(QMainWindow)`** — one window, three tabs sharing a profile/identity panel at the top (SSH user/host/remote root/password). That panel is collapsible via a checkbox (it's filled in once and rarely revisited, so collapsing it gives the tabs below more vertical room); the collapsed/expanded state persists in `QSettings` like the other UI preferences, defaulting to expanded. The three tabs:
  1. **串接專案 (Connect)** — pick a local folder, git-init/add-remote/push it to a new/existing bare repo on the NAS.
  2. **瀏覽倉庫 / Clone URL (Browse)** — list remote repos (flags empty repos and GitHub mirrors; sortable by name/size/recent-activity), filterable by a `QTabBar` of origin-kind tabs (全部/自己的/我 fork 的/clone 別人的/鏡像/未分類, each with a live count — see "Repo origin classification" below), rename a repo in place (moves the bare dir and its `ci_policies/<repo>.policy` together), view/set per-repo CI policy, view repo details (now includes the repo's `description` file content), edit that description, set git-native branch protection, browse files and preview file content without cloning (renders `.md` as Markdown, supports `git blame`), browse commit log, list merged branches, diff two refs, run `git gc`, run `git fsck --full` as a read-only integrity check (flags real corruption separately from harmless dangling/unreachable objects), manage annotated tags as lightweight releases, full-text search across all repos with clickable results that jump straight to the matching line, see a cross-repo recent-activity dashboard, manage the current SSH identity's own `authorized_keys` (now shown with SHA256 fingerprints), clone locally, archive/delete repos, batch-clean checked archive entries, register a GitHub mirror (`git clone --mirror` on the NAS) and sync selected/all mirrors on demand, and configure a per-repo offsite backup destination (`git push --mirror` to an external Git endpoint such as a private GitHub repo) with on-demand sync of selected/all configured repos, set/override a single repo's origin classification, and batch-suggest classifications for everything still unclassified via GitHub API + local-disk evidence. New-repo creation can optionally seed an initial commit from a README.md/.gitignore template.
  3. **維運 / 日誌 (Maintenance/Logs)** — health check (nine sections: per-repo hook/group/`core.sharedRepository` audit, LFS-candidate large-file scan, a `.bat` CRLF-risk scan — flags repos with `.bat` files but no `*.bat text eol=crlf` in `.gitattributes`, since a purely-LF `.bat` can parse incorrectly on a checkout machine with different `core.autocrlf` — a `git_devs` home-directory ACL scan (see the reporting invariant below), a scheduled-script drift check (SHA-256 of NAS `tools/*.sh` vs the in-repo copies, LF-normalized on both sides; either side unreadable → reported as cannot-confirm, never `[OK]`), mirror-staleness (≥14 days since `FETCH_HEAD` moved), offsite-backup health (configured but no `nasgit.lastbackup` success stamp, or stale ≥14 days), `_archived/` size/count, and a ≥90% disk-usage warning), server disk-usage dashboard (`df` free space + total Git_Server usage + top-10 largest repos), one-click repair (reapply hook templates + fix group perms; the confirm dialog defaults to a **dry-run** that reports per-repo `[WOULD-FIX]` reasons vs `[OK]` without touching anything — the full run overwrites every repo's hooks unconditionally, so its all-`[FIX]` report can't distinguish "was fine" from "was fixed"), deploy the scheduled server-side scripts (`deploy_tools` mode — pushes the four `TOOL_SCRIPT_NAMES` files to NAS `tools/` with timestamped backups, `[SAME]` skip on identical content; DSM 任務排程表 entries still have to be registered by hand once; the frozen exe carries the scripts via `--add-data` in `build_exe.bat`, and `tool_script_path()` resolves `sys._MEIPASS` first then the program directory), create a new `git_devs` account (with an optional one-click local SSH keygen), view/remove existing `git_devs` accounts, view/clear the local password-record file those account creations leave behind, edit the shared Telegram notification config, tail server logs, view the local audit log.
- Every long-running UI action follows the same pattern: collect a `cfg` dict → spawn a `Worker(cfg, mode=...)` → connect its signals → `worker.start()`. `set_busy()` disables the relevant buttons while a worker runs.
- **Dialogs** (`DeleteRepoDialog`, `TextViewDialog`, `RepoFilesDialog`, `RepoLogDialog`, `RepoDiffDialog`, `CreateTagDialog`, `TagDialog`, `ActivityDialog`, `SshKeysDialog`, `CreateGitDevsUserDialog`, `GitDevsUsersDialog`, `RemoveGitDevsUserDialog`, `AddKeyForUserDialog`, `RotateKeyDialog`, `GitDevsCredLogDialog`, `GrepResultsDialog`, `SetCiDialog`, `CreateRepoDialog`, `BranchProtectDialog`, `NotifyConfigDialog`, `ArchiveDialog`, `MirrorDialog`, `BackupDialog`, `RepoKindDialog`, `RepoKindScanDialog`) are small, single-purpose, and follow the same Worker pattern for anything that hits the network. `RepoFilesDialog`/`RepoLogDialog`/`RepoDiffDialog`/`TagDialog`/`ActivityDialog`/`SshKeysDialog`/`CreateGitDevsUserDialog`/`GitDevsUsersDialog`/`RemoveGitDevsUserDialog`/`AddKeyForUserDialog`/`RotateKeyDialog`/`GrepResultsDialog`/`BranchProtectDialog`/`NotifyConfigDialog`/`BackupDialog`/`RepoKindDialog`/`RepoKindScanDialog` self-manage their own Worker calls rather than going through `MainWindow`'s `on_ci_result`/`on_ci_done` pair. `TextViewDialog(markdown=True)` swaps the read-only `QPlainTextEdit` for a `QTextBrowser.setMarkdown()` render, used for `.md`/`.markdown` file previews; `TextViewDialog(goto_line=N)` scrolls/positions the cursor at that line, used by `GrepResultsDialog` to jump straight to a search hit.

### Server-side CI system

The NAS runs a shared `pre-receive.ci` hook engine (one copy for all repos) that self-loads a per-repo policy file from `ci_policies/<repo>.policy` (`POLICY=none|soft|strict`). `PATCHED_ENGINE_B64` in this file is a base64-encoded copy of that engine script, pushed to the NAS by the "升級 CI 引擎" (upgrade engine) action — keep it in sync with `hooks_template/pre-receive.ci` on the server if that script changes. Policy rules enforced: branch name must match `develop|feature/*|release/*`, commit message must start with `feat:`/`fix:`/`chore:`/`docs:` or contain `[JIRA-n]`/`[TASK-n]`. `soft` warns via Telegram (real-time, one message per `violate()` call) only; `strict` blocks the push. The engine's Telegram credentials now come from `config/tg_bot.conf` (`CONF="$BASE/config/tg_bot.conf"; [ -f "$CONF" ] && . "$CONF"`) — same file every other script on the server reads, so rotating the bot token via "Telegram 通知設定…" takes effect here too. `send_telegram()` no-ops instead of curling with empty credentials if the config is missing/blank. Keep it that way — this engine used to be the one script with the token hardcoded, which made rotations silently skip CI notifications only ([`docs/INCIDENTS.md`](docs/INCIDENTS.md), 2026-07-15).

The commit-message loop must never assume `$oldrev` is a real commit: on a brand-new branch it's 40 zeros, and on a branch deletion `$newrev` is. The engine handles both explicitly (`$newrev` all-zero → `continue`; `$oldrev` all-zero → `git rev-list "$newrev" --not --all`, which works because pre-receive runs before the new ref exists, so `--all` excludes it). Getting this wrong doesn't fail loudly — `git rev-list` prints `fatal: Invalid revision range 000…`, the `for` loop body never runs, and the engine still `exit 0`s, so the push succeeds with its commit messages entirely unchecked ([`docs/INCIDENTS.md`](docs/INCIDENTS.md), 2026-07-26).

`_run_upgrade_engine` rewrites the engine's `BASE=` line to the current `remote_root` before deploying — the blob hardcodes `/volume1/Git_Server`, and an engine looking at the wrong `BASE` reads no policy at all and silently passes every push.

**Changing the engine means changing it in two places.** `PATCHED_ENGINE_B64` is only the copy this tool *deploys*; the copy that actually runs lives on the NAS and is replaced only when someone clicks "升級 CI 引擎". A fix committed here has no effect on any push until that button is pressed.

### Server-side hook templates kept in this repo

`hooks_template/` holds reference copies of hooks deployed to the NAS. Currently only `hooks_template/post-receive` is checked in (Synology non-blocking version: writes `logs/git_push.log`, sends a Telegram push notification via `config/tg_bot.conf` if configured, backgrounds the `curl` call so a slow/failed Telegram send never delays the pusher's `git push` from returning). The CI engine's `pre-receive.ci` is **not** in this folder or anywhere else in this repo — its only copy lives on the NAS itself plus the base64 blob in `PATCHED_ENGINE_B64` (see "Server-side CI system" above); don't go looking for a `hooks_template/pre-receive.ci` file here, it doesn't exist.

### GitHub mirrors

`sync_github_mirrors.sh` is a standalone server-side script (not run from the GUI) meant to be deployed to the NAS at `/volume1/Git_Server/tools/` and scheduled via DSM 任務排程表. It loops all `*.git` repos, skips any without `remote.origin.mirror=true`, and runs `git remote update --prune` on the rest, logging to `logs/mirror_sync.log` and optionally notifying Telegram (reads token/chat id from `config/tg_bot.conf` on the NAS — never hardcode credentials in this script). It's the scheduled counterpart to the GUI's on-demand "同步鏡像" button (`sync_mirrors` Worker mode), which runs the same `remote update --prune` logic over SSH instead of a local cron job.

### Daily report scripts and the shared email helper

`ci_daily_violation_report.sh` (CI violation daily digest, reads `logs/ci_violation.log`) and `git_stats_report.sh` (push/repo/user/branch leaderboard, reads `logs/git_push.log`) are two more standalone server-side scripts, deployed to `/volume1/Git_Server/tools/` and scheduled via DSM 任務排程表, same convention as `sync_github_mirrors.sh`. Both used to hardcode their own `BOT_TOKEN`/`CHAT_ID` — now both source `config/tg_bot.conf` like every other script in this project, so rotating the bot token in the GUI's "Telegram 通知設定…" takes effect everywhere instead of leaving stale copies behind.

Both scripts now also send the same message body as an email, by piping it through `send_email.py` (`echo "$MSG" | python3 "$BASE/tools/send_email.py" --subject "..."`). `send_email.py` is a small stdlib-only helper (no `pip` on this NAS, so no `requests`/etc.) that reads SMTP credentials from **`/volume1/NAS_Safety/login_watch/config.json`**'s `smtp` block — a deliberate cross-project reuse of the `login_watch` project's already-working Gmail SMTP setup rather than maintaining a second copy of the same credentials. It exits 0 even on failure (missing config, SMTP error) so a broken mail path never fails the calling bash script or blocks its Telegram send.

`NAS_Safety/login_watch/login_watch.py` (a separate project with its own deployment path on the NAS and its own `README.md` — its source just happens to be tracked inside this same git repo) got the mirror-image fix: it already emailed on new-login events via its own `config.json` SMTP block, and now also POSTs to Telegram using `load_telegram_config()`/`send_telegram()`, reading the *same* `/volume1/Git_Server/config/tg_bot.conf` these NAS_GIT_Tools scripts use — again to avoid a second Telegram credential living in a different project. The two notification paths are independent: either one missing/failing doesn't block the other, and neither blocks writing the JSONL record or advancing `state.json`.

### Offsite backup (the reverse direction of GitHub mirrors)

`create_mirror`/`sync_mirrors` pull an external GitHub repo *into* the NAS (`git clone --mirror <url>`, marked by `remote.origin.mirror=true`). Offsite backup goes the other way: an existing NAS-hosted repo (one people actually push to, not itself a mirror) gets a `git push --mirror` destination configured, so it can be periodically pushed *out* to an external endpoint (typically a private GitHub repo) as a disaster-recovery copy — covers the gap where an NAS disk failure would otherwise take `_archived/` down with it too, since archived items never leave the NAS.

- `BackupDialog` (per repo, "離站備份…" button next to `branch_protect_btn`, same enable/disable gating as `desc_btn`/`branch_protect_btn` — i.e. gated only in `on_repo_selected`, not in `set_busy`) reads/writes the destination URL as a plain git remote named `offsite-backup` on the bare repo (`get_backup_remote`/`set_backup_remote` Worker modes, `_run_get_backup_remote`/`_run_set_backup_remote`) — same URL whitelist regex as `create_mirror`. Saving with an empty URL removes the remote (`git remote remove offsite-backup`). A successful save calls `audit_log()` directly (see the config-change audit note below).
- "同步離站備份" (`backup_sync_btn`, top-level button next to `mirror_sync_btn`, gated only by busy state like its mirror counterpart) triggers `backup_sync` Worker mode (`_run_backup_sync`), which mirrors `_run_sync_mirrors`'s structure but filters repos by `remote.offsite-backup.url` being set (instead of `remote.origin.mirror=true`) and runs `git push --mirror offsite-backup` (instead of `remote update --prune`), stamping `nasgit.lastbackup` (epoch) on each successful push — the health check uses that stamp to flag configured-but-never-pushed repos. Empty selection syncs every repo that has a backup destination configured, matching the "空=全部" convention `sync_mirrors` already uses.
- `git push --mirror` makes the destination byte-for-byte match the source, including deleting branches/tags that only exist at the destination — `BackupDialog` warns about this and tells the admin to point it at a dedicated, otherwise-unused backup repo, not a live shared repo.

### Repo origin classification (own / fork / clone / mirror)

Every non-mirror bare repo can carry a `nasgit.kind` (`own`/`fork`/`clone`, unset = 未分類), `nasgit.upstream` (source URL, fork/clone only), and `nasgit.kindsrc` (`auto-connect`/`auto-github`/`auto-local`/`manual` — where the value came from) in its own git config, read by `_run_list` and shown in **瀏覽倉庫**'s origin-kind tab bar and per-row marker (`🏠自己`/`🍴fork`/`📥clone`/`↺鏡像`). **Mirror is never stored in `nasgit.kind`** — `effective_repo_kind()` always treats `remote.origin.mirror=true` as authoritative and overrides whatever `nasgit.kind` says, so the two mechanisms can't disagree; `_run_set_repo_kind` refuses to write `nasgit.kind` on a mirror repo for the same reason.

This exists because `_run_connect` used to silently destroy the one signal that could answer "did this come from somewhere else": when a local folder already had an `origin` (the common case for a `git clone`d fork) the connect flow's `git remote set-url origin <NAS_url>` overwrote it with no record kept anywhere. Three ways a repo's `nasgit.kind` gets set, in order of how much signal is available:

- **At connect time** (`_run_connect` → `_repo_kind_config_lines`, only if `nasgit.kind` isn't already set on the NAS side — never overwrites a previous classification; the existing-kind check and the config write are folded into `_run_connect`'s two consolidated SSH scripts — the whole connect flow now uses two round-trips instead of the original eight, so don't add a third for a new per-connect fact, extend one of the scripts): captures the pre-overwrite `origin` URL as `prev_origin` before it's replaced. Empty `prev_origin` → `own`. A `github.com` `prev_origin` whose owner matches the configured `github_login` (`collect_identity_cfg()` reads `github_login`/`github_token` from `QSettings`, populated only via the batch dialog below) gets one live GitHub API call to check the repo's `fork` flag (`fork` → `fork` + `parent.clone_url` as upstream, non-fork → `own`); any other case (API call fails/rate-limited, owner doesn't match, or a non-GitHub host) degrades to `clone` + the raw URL, logged as a best-effort guess the admin can correct later.
- **Per-repo manual override** (`RepoKindDialog`, "來源分類…" button next to `backup_btn`, gated like `backup_btn` in `on_repo_selected`): reads the kind/upstream already carried in the selected `QListWidgetItem`'s `UserRole+3`/`+4` data (no extra round-trip to load), four-way radio (own/fork/clone/未分類) + upstream URL field, writes via `set_repo_kind` with a single-item list. Read-only (all controls disabled, Save button hidden) when the selected repo is a mirror.
- **Batch retroactive classification** (`RepoKindScanDialog`, "來源批次比對…" button in `top_row2`) — for the repos that already lost their origin before this feature existed and can't be auto-detected anymore. Combines two independent, best-effort evidence sources rather than trusting either alone — the two scans run in **parallel** (separate Workers; one side failing still builds the table from the other side's evidence, with the failure shown in the status line): `github_scan` (the configured GitHub account's repo list — `/user/repos?affiliation=owner` when a token is present so private repos are visible, `users/<login>/repos` otherwise, with pagination judged on the raw pre-filter batch size; only forks that also match a current NAS repo name get the extra parent-lookup call, to avoid burning the unauthenticated 60-req/hour budget on a large account) and `local_scan` (walks local project folders for **any** remaining `remote.*.url` that isn't the NAS host — deliberately not limited to `origin`, since the actual clue for an already-connected repo is usually a leftover `upstream` remote from the fork workflow, `origin` having already been repointed at the NAS). Repo-name matching between GitHub/local-folder names and NAS bare-repo names is case-insensitive on both sides. Results only pre-check the "套用" box where there's a suggestion *and* the repo is currently unclassified — an already-classified repo still gets a suggestion shown for review, but doesn't get silently overwritten by default. GitHub login/token are opt-in remembered in `QSettings` (`github_login`/`github_token`) via a "記住" checkbox, same pattern as the NAS password.

### Multi-identity push permissions

Repos are pushed to from multiple SSH identities (e.g. 家中/kuoterry and 公司/Git_User1), each a different Unix user sharing the `git_devs` group. Git's default loose-object permissions are owner-only-write, so a bare repo touched by two different users can end up with subdirectories (`objects/xx/`) that one identity can't write into even though both are in `git_devs` — group membership doesn't let you `chmod`/`chown` files you don't own, only root or the owner can. `_run_create_repo` and `_run_connect` set `core.sharedRepository=group` right after `git init --bare` so all objects git creates from then on are group-writable; `_run_repair` re-applies that config to every existing repo, and `_run_healthcheck` flags any repo missing it. None of this retroactively fixes directories that already exist with the wrong mode — that still needs a one-time privileged `chmod -R g+rwX` (as root, or as the original owning identity) on the affected repo.

### Creating new `git_devs` accounts

`CreateGitDevsUserDialog` does **not** create DSM accounts itself — the tool has no passwordless sudo on this NAS (verified: `sudo -n true` fails), so anything requiring root can't run silently in the background. Instead it: (1) runs `prep_new_user` (read-only) to fetch the current `git_devs` membership and check whether the requested username already exists via `id`; (2) generates a random 16-char alnum password client-side (`secrets.choice`, not on the NAS) and immediately appends it in plaintext to a local-only file, `GIT_DEVS_CRED_LOG_PATH` (`~/.nas_git_connector/git_devs_credentials.log`, via `save_git_devs_credential()`) — this is a deliberate accepted tradeoff (the user explicitly asked for a durable record over the more conservative "never persist the secret" option) and the dialog/note text both say so plainly so it isn't a silent surprise; (3) builds a shell script — `sudo -v` first to cache sudo credentials, `synouser --add` for the DSM user with that password embedded directly (alnum-only, no escaping needed), `synogroup --member git_devs <ALL existing members> <new user>` (this Synology command *replaces* the member list rather than appending, so the script always includes the full existing membership it just queried) followed by an automatic re-read of `/etc/group` that loudly warns if anyone expected is missing, SSH key setup via `sudo tee` under the account's actual home directory (detected via `/etc/passwd`), and the same `chmod -R g+rwX` / `core.sharedRepository=group` sync from the multi-identity fix above; (4) shows that script in a `TextViewDialog` for the user to copy and paste **as one block** into their own privileged SSH session — by design there is exactly one interactive checkpoint in the whole script (the `sudo -v` password prompt at the very top), everything after it runs unattended. `synouser`'s exact argument order is DSM-version-dependent and unverified against this NAS, so the generated script tells the user to check `synouser --help` first if it errors.

The dialog also has a "本機產生新金鑰…" button (`local_gen_ssh_key` Worker mode, `_run_local_gen_ssh_key`) that shells out to local `ssh-keygen -t ed25519 -N "" -f <path>` to save a round-trip through a separate terminal — it refuses to overwrite an existing file at that path (checks both the private-key path and `<path>.pub` before running), then reads the generated `.pub` file back and fills the pubkey textbox automatically. This runs entirely on the admin's own machine via `self._run()` (same local-subprocess helper `_run_clone` uses for `git clone`) — it never touches the NAS, and the private key never leaves this machine or gets embedded in the generated script (only the public key content is used downstream). If the account being created is for someone else, the private key still has to be handed off out-of-band by the admin; the tool only removes the "open a terminal and run ssh-keygen yourself" friction, not the handoff step.

This feature broke on each of its first three real-world runs, each time a different bug (group membership silently wiped, a password placeholder executed verbatim, `sudo` prompts corrupting a paste, `$HOME_DIR` expanding to empty inside `sh -c`) — narratives in [`docs/INCIDENTS.md`](docs/INCIDENTS.md) (2026-07-11). The three rules they produced apply to **every** remote command and generated script in this file, not just this dialog:

**Lessons for any future remote command or generated script in this file:**
- Never depend on `getent` (or other NSS-lookup binaries) in the SSH remote-execution path — this DSM's non-interactive shell `PATH` doesn't include it. Use `grep`/`awk`/`cut` against `/etc/passwd` and `/etc/group` directly, same as everywhere else in `Worker`.
- A script meant to be pasted as one block should have **at most one** interactive/password checkpoint, placed as the very first line (`sudo -v`) — every additional prompt is a chance for terminal paste buffering to corrupt subsequent lines. Prefer auto-generating secrets over asking the user to type them mid-script.
- Never reference a shell variable set in the *outer* script inside a nested `sh -c '...'` or `sudo -u ... sh -c '...'` single-quoted string — it won't be expanded there, and won't be in that subshell's environment either. Let the outer shell expand the path/value and pass it as a plain argument instead (e.g. `sudo tee "$PATH_VAR"` not `sudo sh -c 'cmd "$PATH_VAR"'`).

**Three preconditions for key login, each found the hard way, each with the same user-visible symptom** ("generated the script, ran it clean, key still doesn't work") — narratives in [`docs/INCIDENTS.md`](docs/INCIDENTS.md) (2026-07-15, and two separate ones on 2026-07-16). `synouser --add` satisfies none of them, and none is discoverable from the client side, so the generated scripts set all three explicitly:

1. **Home-directory ACL** — `sudo synoacltool -del "$HOME_DIR"` + `sudo chmod 700 "$HOME_DIR"`. DSM's sshd checks Synology's ACL layer on the home directory *itself*, and silently discards the whole `authorized_keys` file if it's non-trivial.
2. **Home-directory ownership** — `sudo chown <user>:users "$HOME_DIR"`. `synouser --add` leaves it `root:root`, which also makes sshd reject the key.
3. **Login shell** — `sudo sed -i 's#^\(<user>:.*:\)/sbin/nologin$#\1/bin/sh#' /etc/passwd`. Some accounts come out of `synouser --add` with `/sbin/nologin` (reason unknown, not controlled by any documented argument), which refuses to exec anything over SSH — including `git-receive-pack`, so pushes fail too.

All three are applied by both `CreateGitDevsUserDialog._build_script` (new accounts) and `AddKeyForUserDialog._build_script` — the latter matters because it's the only path that can *repair* an account created before these fixes existed. `RemoveGitDevsUserDialog`/`RotateKeyDialog` don't need them (they never provision a fresh home directory or `.ssh`).

Because that symptom has now had three distinct root causes, both `_build_script` methods end with a shared `_login_precondition_selfcheck(username)` helper that re-checks all three at generation time and prints a ✅/‼️ summary — so the *next* unknown cause is at least ruled out against everything already known, instead of being rediscovered by a login failure weeks later. Note its `authorized_keys` check must run as `sudo test -s ...`, not a bare `[ -s ... ]` — the file lives inside the target user's `700` `.ssh` directory, which the admin's own non-root shell cannot traverse, so an unprivileged check would always report "missing" even when the file is fine.

The free-text 描述/email fields in the `synouser --add` line go through `shq()` — the script is meant to be pasted and run as one trusted block under `sudo`, so an unescaped `` ` `` or `$(...)` in a description would execute (code review, 2026-07-16).

Precondition 1 is also scanned fleet-wide by `_run_healthcheck`'s fourth section, which walks `git_devs` members out of `/etc/group` and runs `synoacltool -get "$home"` on each. **A check that cannot read its data must report "cannot confirm", never `[OK]`.** This tool's SSH identity is not root and has no passwordless `sudo` on this NAS, so it genuinely cannot read another account's home ACL — empty `synoacltool` output is counted into `acl_skip` and reported separately, and the "所有 git_devs 帳號的 home 目錄 ACL 正常" line is emitted only when `acl_bad` **and** `acl_skip` are both zero. Getting this wrong is worse than not having the check: a health report that says everything is fine is exactly what stops someone from looking, and this precondition's symptom is already silent by nature (sshd discards the key and falls back to password auth without logging anything). Applies to every future healthcheck section, not just this one.

### `git_devs` account lifecycle beyond creation

Three more pieces complete the loop that account creation started:
- **`GitDevsUsersDialog`** ("git_devs 帳號清單…") — read-only, `list_git_devs_users` Worker mode. Parses `/etc/group` for the member list, then for each member greps `/etc/passwd` for uid/home and counts non-blank/non-comment lines in `<home>/.ssh/authorized_keys` as a rough key count. No caching — always a fresh SSH round-trip, since this is exactly the thing that would have made the earlier incidents easier to catch in real time instead of via manual `cat /etc/group`.
- **`RemoveGitDevsUserDialog`** ("移除選取帳號…", opened from the list dialog) — mirrors the creation flow's safety design deliberately: reuses the `prep_new_user` Worker mode (just pass the target as `new_user`) to read current membership, refuses to generate a script if removing the target would leave `git_devs` empty, and the generated script has the same `sudo -v` single-checkpoint + post-`synogroup --member` self-verification loop as account creation — plus an extra check specifically confirming the removed user is actually gone. Removing from `git_devs` only revokes repo-push permission via group membership; it does **not** revoke SSH login to the NAS shell itself (the account and its `authorized_keys` are untouched unless the user checks "同時刪除 DSM 帳號本身", which adds `sudo synouser --del <user>` — irreversible, off by default). The dialog also confirms before generating a script for `kuoterry`/`Git_User1` specifically, since those are this tool's own default-profile identities.
- **`GitDevsCredLogDialog`** ("git_devs 密碼留底紀錄…") — views and can delete `GIT_DEVS_CRED_LOG_PATH` wholesale. Deletion goes through `audit_log()` directly (not a Worker mode, so it's not covered by `DESTRUCTIVE_MODES` — this dialog calls `audit_log()` itself after removing the file).
- **`AddKeyForUserDialog`** ("幫選取帳號新增金鑰…", opened from the list dialog) — same script-gen-only pattern as account creation/removal, but needs no NAS query first (the target username is already known from the list). Exists specifically for the case `SshKeysDialog` can't cover: adding a key to an account the admin can't currently log into themselves. The generated script re-detects `HOME_DIR` from `/etc/passwd` (never trusts a cached value) and appends via `sudo tee -a` after a `grep -qxF` dedupe check, so re-running it against a key that's already present is a no-op instead of a duplicate line.
- **`RotateKeyDialog`** ("金鑰輪替…", opened from the list dialog) — one script that adds a new pubkey and (optionally, if the old one is pasted in) removes the old one from the same `authorized_keys`, backing up the file first (`cp "$AK" "$AK.bak-<timestamp>"`) exactly like `_run_ssh_keys_delete` already does for the self-service path. Deliberately scoped to just this: it does **not** touch Key_Management's `registry.json` to mark the old key rotated/archived — that's a manual follow-up in Key_Management itself, kept out of this tool on purpose to avoid one tool silently mutating the other's state.
- **Key_Management import bridge** — `CreateGitDevsUserDialog`, `AddKeyForUserDialog`, `RotateKeyDialog`, and `SshKeysDialog` all have a "從 Key_Management 匯入…" button next to their pubkey field, backed by `pick_key_management_pubkey()` → `key_management_registry_pubkeys()`. This reads `~/.key_management/registry.json` (Key_Management's own persistent key inventory, keyed by fingerprint) read-only, filters to `status == "active"` entries whose `pub_path` file exists and parses as a single-line OpenSSH pubkey, and lets the admin pick one from a list instead of alt-tabbing to copy-paste. `.ppk` and multi-line RFC4716 pubkeys are silently skipped (not converted) — out of scope for this bridge. This is the first of two deliberately-scoped, one-directional exceptions to the two tools' independence (see the top-level note); it only ever reads that one file, never writes it. The second, added alongside cross-machine profile sync, runs in the opposite direction — see "Cross-machine profile sync" below.

### Branch protection is independent of the CI policy engine

`BranchProtectDialog` sets git's own `receive.denyDeletes` / `receive.denyNonFastForwards` config directly on a repo (`branch_protect_get`/`branch_protect_set` Worker modes) — this is a *separate* mechanism from the `PROTECT_MASTER` field inside the CI engine's `ci_profiles/<policy>.conf` (which `_run_repo_detail`/`hooks` report read-only and this tool has never had a GUI to edit, since it's a shared profile file affecting every repo on that policy, not a single repo). Native git denies happen at the transport level regardless of CI policy/soft/strict; the CI engine's checks are a separate pre-receive hook layer on top. Don't conflate the two when troubleshooting a rejected push — check both.

### Repo description, disk usage, and Telegram notification config

- Bare repos have a built-in `description` file (plain text, purely informational — never affects git behavior). `_run_repo_desc_get`/`_run_repo_desc_set` read/write it; `on_edit_desc` fetches the current text into a `QInputDialog.getMultiLineText` prefilled editor. Content is base64-transported in both directions to sidestep multi-line/quoting issues.
- "伺服器空間總覽" (`disk_usage` mode) runs `df -h` on `remote_root`'s filesystem plus `du -sh` totals and a top-10 largest-repo ranking — read-only, no state changes.
- "Telegram 通知設定…" (`NotifyConfigDialog`, `tg_conf_get`/`tg_conf_set` modes) edits `config/tg_bot.conf` (`BOT_TOKEN=`/`CHAT_ID=`), the same file `sync_github_mirrors.sh` and the CI engine both read for notifications — backs up the old file (`.bak-<timestamp>`) before overwriting, same convention as `SshKeysDialog`.

### Repo creation templates

`CreateRepoDialog` can optionally seed a brand-new bare repo with an initial `chore: 初始化 repository` commit (README.md with a title, and/or a `.gitignore` from the `GITIGNORE_TEMPLATE` constant — which is now just an alias of `GITIGNORE_TEXT` (the Keil/Python/ESP-IDF one the connect flow writes), deliberately one content for both paths so they can't drift). Since a bare repo has no working tree, this is done with git plumbing over SSH — `git hash-object`/`update-index`/`write-tree`/`commit-tree`/`update-ref` against a scratch `GIT_INDEX_FILE` (must come from `mktemp -u`, i.e. a path only, never a pre-created empty file — git's index reader treats a 0-byte file as a corrupt index, not an empty one) — with `GIT_AUTHOR_*`/`GIT_COMMITTER_*` explicitly set in the command since the server-side git user has no configured identity. This bypasses the pre-receive hook entirely (it's not a push), which is fine since template seeding happens before any CI policy could apply.

### Safety mechanisms baked into the code

- `CONTAINER_ROOTS` (`D:\git`, `D:\GIT`) and disk roots are hard-blocked from being connected as a "project" (`is_container_root`) — prevents accidentally git-initing an entire drive/container folder.
- `find_nested_repos` detects git repos nested inside the chosen folder and forces a "I understand the risk" checkbox before proceeding (they'd otherwise become gitlinks).
- `is_safe_name` whitelists repo/archive names via `^[^\W_][\w.-]*$` (Unicode-aware — first char must be alnum/CJK, not `_` or punctuation; rest can include `.`/`-`), rejecting `.`, `..`, `_archived` — every remote path built from user input goes through this before being interpolated into a shell command.
  `_run_connect` was the last mode to get this check ([`docs/INCIDENTS.md`](docs/INCIDENTS.md), 2026-07-16 code review).
- Repo deletion (`DeleteRepoDialog` → `_run_delete`) has **three** modes, chosen by radio button and passed as `delete_mode`: `archive` (default — `mv` into `_archived/<name>.<ts>`, fully reversible), `backup_delete` (`tar -czf` into `_archived/<name>.<ts>.tar.gz`, then `rm -rf`), and `hard_delete` (bare `rm -rf`, unrecoverable). Note the confirmation gate is **not** hard-delete-specific: `_update_ok` keeps the 執行 button disabled until the exact repo name is typed, for all three. `_run_delete` also refuses to touch anything that isn't a real bare repo (`[ -e '<path>/HEAD' ]`) before running any of them, so a mistyped-but-safe-looking name can't `rm -rf` an unrelated directory.
- `ArchiveDialog` flags (but never auto-deletes) archived items older than `ARCHIVE_STALE_DAYS` (90 days), parsed client-side from the `<name>.YYYYMMDD-HHMMSS[.tar.gz]` timestamp suffix that `_run_delete` appends on archive. Batch cleanup (`on_bulk_purge`) requires each item to be individually checked in the list — there's no "select all and purge" in one click by design. The purge itself runs as **one** `archive_purge` Worker carrying `arch_names` (a single SSH connection looping server-side, `[OK]`/`[FAIL]`/`[NOTFOUND]` per item, per-item audit via the `hooks` payload) — not one Worker per item.
- SSH passwords are masked in the log output (`_mask`) and only persisted to the registry (`QSettings`) if the user explicitly opts in via "記住此身份的密碼".
- `SshKeysDialog` only ever touches `$HOME/.ssh/authorized_keys` for the *currently connected* SSH identity (never another user, never system-wide) and backs up the file (`.bak-<timestamp>`) before removing a key. Each listed key shows its SHA256 fingerprint (`ssh_fingerprint()`), computed entirely client-side from the already-fetched key line — no extra NAS round-trip.
- `audit_log()` appends a local, timestamped line to `~/.nas_git_connector/audit.log` (outside this repo) whenever a Worker mode in `DESTRUCTIVE_MODES` (`delete`, `rename_repo`, `repo_gc`, `tag_delete`, `ssh_keys_delete`, `archive_purge`) finishes — the NAS side only records pushes, not admin actions taken through this GUI, so this is the only local trail of what got deleted/renamed/gc'd and when. Viewable via "本機操作稽核紀錄" in the Maintenance tab. Config-changing (non-destructive) actions that don't go through the generic `on_ci_done` handler — `set_ci`/`set_ci_batch` (`on_set_ci_done`/`on_batch_done`), `repo_desc_set` (`on_desc_set_done`), `branch_protect_set` (`BranchProtectDialog._on_saved`), `tg_conf_set` (`NotifyConfigDialog._on_saved`), `set_backup_remote` (`BackupDialog._on_saved`) — each call `audit_log()` directly in their own success branch instead, since they're not in `DESTRUCTIVE_MODES` and each has its own bespoke `done` handler rather than sharing `on_ci_done`. `tg_conf_set`'s audit line deliberately logs only whether the token/chat-id were set or blank, never the token value itself, so the secret doesn't end up duplicated into the audit log.
  `on_ci_done`'s `audit_log()` call is gated on `if ok:`, and `_run_repo_gc` separately calls `audit_log()` itself when `nfail > 0 and nok > 0` — batch `repo_gc` emits `done(nfail == 0, ...)`, so a partially-failed batch would otherwise leave no record of the repos that *did* get gc'd. Making `on_ci_done` log unconditionally instead was tried and reverted: it logged client-side validation and connection failures for the other five (atomic) modes, where nothing ran on the NAS at all ([`docs/INCIDENTS.md`](docs/INCIDENTS.md), 2026-07-16 code review).
- Healthcheck's LFS section flags repos with any tracked file over `LFS_SUGGEST_BYTES` (5 MB) — advisory only, doesn't touch the repo.
- `_run_grep_all` parses `git grep` output (`tree:path:line:content`) without colon-splitting: the remote awk step strips the `$base:` tree prefix by exact length, and the Python side finds the path/line boundary with `re.match(r"^(.*?):(\d+):(.*)$", grepline)`. Two known limitations, both accepted rather than fixed: a path containing a `:digits:` substring *before* the real line-number field (e.g. `notes:2024:report.py`) still mis-splits, and `core.quotePath=true` octal-escapes non-ASCII paths, so a hit in a CJK-named file can't be resolved back by `GrepResultsDialog`'s "開啟". Rationale for stopping there in [`docs/INCIDENTS.md`](docs/INCIDENTS.md) (2026-07-16 code review).

### Persistence

Settings/profiles (SSH user/host/remote root, optional saved password, optional identity file path, per-machine profile binding, last-used folder, identity-panel collapsed state) are stored via `QSettings("TerryTools", "NasGitConnector")` — on Windows this is the registry, not a file in this repo. Multiple named "profiles" (e.g. 家中/公司) can each auto-select based on `socket.gethostname()`.

### Per-profile identity file

`_ssh()` and `_git_env()` have always relied entirely on SSH's own default key resolution (agent + `~/.ssh/config` + default-named files like `id_ed25519`) — they never passed `-i`. That's fine for `kuoterry`/`Git_User1` since their keys happen to be default-named or agent-loaded, but it silently breaks for any `git_devs` account whose key has a non-default filename (e.g. `id_ed25519_git_user2`, generated via `local_gen_ssh_key`/`AddKeyForUserDialog`) — SSH has no way to discover it without either an SSH config entry or the key being in the agent, and the tool's own NAS-connection test (`_run_test`, `BatchMode=yes`) would just fail outright rather than falling back to a password prompt. The identity panel now has an optional "私鑰檔案" field (`identity_file_edit`, persisted per-profile alongside user/host/remote_root); when set, `_ssh()` appends `-i <path> -o IdentitiesOnly=yes` to the `ssh` invocation and `_git_env()` sets `GIT_SSH_COMMAND` to the equivalent for local `git push`/`clone`. Password takes precedence over identity file when both happen to be set (they're mutually exclusive auth paths in practice); leaving it blank preserves the exact prior behavior for identities that already work.

### Cross-machine profile sync (`profile_sync_pull`/`profile_sync_push`)

For a single admin using multiple machines (home/office), the "☁ 同步跨機器設定" button next to the profile combo (`MainWindow.on_sync_profiles`) syncs profile settings — `user`/`host`/`remote_root`/`machines` (the hostname-binding list `_profile_machines` already used for auto-selecting a profile) — through a shared file on the NAS, `<remote_root>/config/profiles_sync.json`, written/read the same base64-transport + `mkdir -p` + timestamped-backup-before-overwrite convention as `tg_conf_set`. **Password and `identity_file` are deliberately never included** — the former is a secret, the latter is a machine-local filesystem path that means nothing on a different machine. Every `_write_profile()` call stamps an `updated_at` (UTC ISO8601); sync is a single click that does pull → merge → push in one flow (`on_sync_profiles` → `_on_profile_sync_pull_done` → `_on_profile_sync_push_done`): merge is per-profile-name, newest `updated_at` wins for `user`/`host`/`remote_root`, and `machines` is always a **union** (never shrinks from a sync, so one machine's push can't silently evict another machine's hostname binding). QSettings reads/writes happen synchronously on the UI thread as already established elsewhere in this file (`add_profile`, `bind_current_machine`, etc.) — only the actual NAS round-trip (the SSH pull and the SSH push) goes through `Worker`, matching the "Worker only touches network/filesystem/subprocess" rule; the merge computation itself is plain Python in `MainWindow._merge_profiles`.

This is also the origin of the one deliberate, narrow *reverse* coupling with `Key_Management`: that tool's own cross-machine key-registry sync (see its `CLAUDE.md`) has a "從 NasGitConnector 帶入…" button that peeks read-only at this tool's `QSettings("TerryTools","NasGitConnector")` profiles to avoid asking the admin to type NAS connection info twice — mirroring, in the opposite direction, the existing `key_management_registry_pubkeys()` bridge described above. Neither tool imports the other; both peeks are read-only and neither is a hard dependency.

### SSH config auto-write for locally-generated keys

`append_ssh_config_match_block(hostname, user, identity_path)` / `offer_write_local_ssh_config(parent, hostname, user, key_path)` — after `local_gen_ssh_key` produces a new keypair in `CreateGitDevsUserDialog`/`AddKeyForUserDialog`/`RotateKeyDialog`, a `QMessageBox.question` (default **No**) asks whether *this* machine should also be able to `ssh`/`git push` as that account without manually passing `-i`. Saying yes appends a `Match originalhost <host> user <user>` + `IdentityFile "<path>"` block to `~/.ssh/config` — this is a different, more general mechanism than the tool's own per-profile "私鑰檔案" field above, since it also covers plain `ssh`/`git` invoked directly from a terminal outside this GUI. Refuses to rewrite if a block for that exact host+user already exists (tells the admin to edit manually rather than risk clobbering something else). Defaults to No because the common case for these three dialogs is generating a key *for someone else* to take away, not for logging in from this machine.

### One-click admin terminal for generated scripts

`open_admin_terminal(cfg)` spawns a new visible console window running `ssh user@host` (or `plink -pw` if a password is configured) using whatever identity is currently connected in the main window — same auth-selection logic as `Worker._ssh()`, just run via `subprocess.Popen(..., creationflags=subprocess.CREATE_NEW_CONSOLE)` instead of captured/piped. `TextViewDialog` takes an optional `terminal_cfg` constructor arg; when set, it adds a "開啟終端機（user@host）…" button next to "複製全部". `CreateGitDevsUserDialog` and `AddKeyForUserDialog` pass `terminal_cfg=self.cfg` when showing their generated setup scripts, so the admin can open a ready-to-paste `sudo`-capable SSH session in one click instead of alt-tabbing to their own terminal. Windows-only (`os.name != "nt"` short-circuits with an error message); other `TextViewDialog` call sites (file preview, audit log, CI rules, etc.) don't pass `terminal_cfg` and so don't get the extra button.
